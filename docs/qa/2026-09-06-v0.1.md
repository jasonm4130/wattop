# End-to-end QA — wattop v0.1

Run 2026-09-06 16:16–16:35 AEST on the target machine (Apple M5 Max, macOS
Tahoe, `go1.27.0 darwin/arm64`), against commit `100f90a` with five live
Claude Code sessions and twelve dormant Codex rollouts on disk.

Everything below is a transcript of what ran. Where a check could not be
run, it says so; nothing here is inferred from reading code.

## Verdict: do not ship yet

> **Superseded.** This is the first run, against `100f90a`. All four
> blockers below were fixed and re-verified on the same machine — see
> **"Re-QA after hardening"** at the end of this file for the current
> verdict and captures. Everything above that heading is the record of the
> run that found them, kept as written.

Four blockers, all found on the live machine and none of them visible to
the test suite:

1. `go test ./...` is **red at HEAD**. `internal/e2e` fails two tests, and
   both were broken by the last two commits.
2. The SoC panel's `Temp` row dumps **~250 raw SMC sensor keys** across the
   whole terminal width instead of CPU/GPU/SOC. It is the first thing on
   screen and it is unreadable.
3. The headline `$/hr` figure reads **$105,679/hr** for about a minute
   after launch, then decays. The number is wrong by roughly three orders
   of magnitude at the moment a new user looks at it.
4. **DRAM bandwidth is not unresolvable on this chip.** It resolves under
   memory load — 32.8 GB/s, then 9–12 GB/s sustained, in 12 of 18 samples —
   and returns to a dash at idle. `docs/limitations.md` states the opposite
   as a hardware fact, and the plan's Deviations §1 builds a whole
   concession on it. When the channel does resolve, `dram_read_gbs` and
   `dram_write_gbs` are **identical to full float precision** on every
   sample, which is one channel written to two fields, not two
   measurements. Evidence in §2.

The first three are shallow: 1 is a regenerate-and-repin, 2 is a filter on
one map, 3 is a seed-the-burn-tracker-on-first-observation fix. The fourth
is not a code bug so much as a **false claim in the shipping docs** about
the one degradation this project argued hardest for, plus a real
read/write duplication behind it.

The measured foundations — coordinated sampling, pid binding, per-session
cost, topology labelling — all hold up under live load.

One long-standing doc claim is now **partly stale in the tool's favour**:
`docs/limitations.md` and `docs/manual-qa.md` item 12 say the session table
cannot fit a terminal under ~150 columns. At HEAD the table narrows
correctly and the 80-column frame is coherent (§3). The frame is not fully
responsive yet, though — the `Temp` row and the `Machine` footer are both
cut mid-token at 80 — so that section wants rewriting, not deleting.

### DRAM bandwidth resolves under load

Both samples above show `dram_read_gbs` and `dram_write_gbs` as `null` with
`sys.missing` naming them, which is what `docs/limitations.md` says to
expect on this chip, permanently. That reading was taken on a near-idle
machine. Under memory load it is false.

A `--json` run with a memory-bandwidth workload (three 200 MB buffers
rewritten in a loop for 20 s) alongside it:

Reproduced a second time with a different load generator (34.8, 5.9,
10.9 GB/s), and first noticed by accident in a pty capture of the TUI,
where the `BW` row read `DRAM R 27.3 GB/s  W 27.3 GB/s  ANE —`.

Two conclusions, and the second is the one that needs fixing in code:

1. **The channel is not unresolvable — it reads a true `0.0` at idle.**
   wattop's rule of treating an exact `0.0` on these fields as "did not
   resolve" is what converts a real idle measurement into a dash. That rule
   was adopted on the strength of an idle-machine observation, and
   `docs/limitations.md` states it as a property of the chip
   (*"the byte-counter channels simply do not resolve on this chip"*). It
   is not.
2. **Read and write are the same number, every time, to the last digit.**
   Twelve of twelve samples had `dram_read_gbs == dram_write_gbs` exactly.
   Real read and write traffic does not match to fifteen significant
   figures; one channel is being assigned to both fields.

`ane_combined_gbs` stayed `null` throughout, so the ANE half of the
deviation is not contradicted by anything measured here.

One defect visible only here: `temps` carries **~250 raw SMC keys**
(`TAOL`, `TB0T`, `TPD0`, `Tg5q`, …) alongside the two semantic `cpu` and
`gpu` entries, and no `soc` entry at all, against a domain contract that
documents the map as `"cpu", "gpu", "soc"`. This is what corrupts the
`Temp` row in §3.

## 3. TUI captures

Run under `tmux 3.7c` on a private socket (`tmux -L wattopqa`), 8 seconds
after launch, `tmux capture-pane -p`. Pasted verbatim — no path in either
capture contains the full username, so nothing needed redacting.

One reading note before the captures: both contain literal TAB characters.
They are **not** wattop output padding. Bubbletea's renderer advances the
cursor with `\t` when the target lands on an 8-column tab stop, tmux
records that in the grid, and `capture-pane` faithfully re-emits it. Proven
two ways: a control `printf "a%20sb"` inside tmux captured back as spaces
(so tmux does not manufacture tabs), and a raw pty capture of wattop's own
byte stream contains 38 `0x09` bytes always preceded by an erase sequence
such as `\x1b[16X\t\t`. Expanded to 8-column stops, both frames measure
their exact terminal width.

about ten seconds, in-process. It is a transient rather than a plateau, but
it is the same number and the README should say so.

### The goldens that changed, and why each change is the fix

**`internal/ui/panel/testdata/TestSoCGolden.golden`** - one line:

```
-BW     DRAM R 0.0 GB/s  W 0.0 GB/s  ANE 0.0 GB/s
+BW     DRAM R --  W --  ANE --
```

This one was a **regression caught before it shipped**, not an intended
change. The SoC fix made `bwdash` render a non-nil `0.0` as a reading, which
is right for the live sampler - it has a `DRAMBWSource` flag saying a
channel was behind the number. `internal/collect/replay` reads mactop's
*headless JSON*, which has no such flag and writes a plain `0` whether a
channel counted zero or never resolved, so every replay frame started
claiming `DRAM R 0.0 GB/s` off a corpus captured where no DRAM byte counter
ever produced data. It also contradicted the ANE paragraph in
`docs/limitations.md`. Fixed at the source instead of accepted into the
golden: `internal/collect/replay/sys.go` now treats an exact `0` on any
bandwidth key as unresolved, nils the field, names it in `sys.missing` and
reports it unresolved from `Channels()`. `TestNonZeroBandwidthResolves` is
the other half - a 12.5 GB/s reading still resolves - so the rule cannot
degenerate into dashing everything.
